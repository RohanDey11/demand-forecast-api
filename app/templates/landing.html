How a request is handled

Every call follows the same four steps — nothing is computed ad hoc.

01
You choose a horizon
Any whole number of weeks you want to see ahead.
02
Request is validated
Anything outside 1–22 weeks is rejected immediately, before it reaches the model.
03
Cached forecast is read
The model refits once a day, not on every request — so answers are fast.
04
You get dates + range
Predicted sales per week, with an upper and lower bound, not just one number.

Why this is a service, not a script

Two decisions that separate this from a Jupyter cell someone re-runs by hand.

Refits on a schedule, not per request

Fitting a fresh model on every single call would make each request slow and unpredictable. Instead, the model refits automatically once a day and every request simply reads from that cached result — fast to answer, current within a day.

Built to survive a heavy dependency

The forecasting engine needs a C++ compiler to build itself on first install. The deploy uses a two-stage build: compile once in a throwaway build stage, then copy only the finished, working environment into the image that actually runs — so the live service stays lean.
